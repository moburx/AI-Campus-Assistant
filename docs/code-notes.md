# Code Notes: Authentication and Assignments

## 1. `backend/auth.py`

### 1.1. `create_access_token`은 토큰에 무엇을 저장하는가? `exp`는 어떤 역할을 하는가?

`create_access_token` 함수는 사용자 ID를 `sub` 필드에 저장하고, 토큰의 만료 시간을 `exp` 필드에 저장한다.

`sub`는 토큰이 어떤 사용자에게 속하는지 식별하는 데 사용된다. `exp`는 토큰이 유효한 기간을 지정한다. 현재 코드에서는 `ACCESS_TOKEN_EXPIRE_MINUTES` 환경 변수로 만료 시간을 설정하며, 기본값은 30분이다. 만료된 토큰을 사용할 수 없도록 하여 보안을 강화한다.

### 1.2. `get_current_user`는 토큰을 어떻게 검증하는가? 어떤 경우에 401 오류를 반환하는가?

`get_current_user` 함수는 요청의 Authorization 헤더에서 Bearer 토큰을 가져온다. 그런 다음 `jwt.decode()`를 사용하여 비밀 키, 설정된 알고리즘 및 토큰의 유효 기간을 검증한다. 검증이 성공하면 `sub` 값을 사용자 ID로 변환하고 데이터베이스에서 해당 사용자를 조회한다.

다음과 같은 경우 HTTP 401 오류를 반환한다.

- 토큰이 유효하지 않거나 만료된 경우
- 토큰에 `sub` 필드가 없거나 사용자 ID를 정수로 변환할 수 없는 경우
- 토큰에 지정된 사용자가 데이터베이스에 존재하지 않는 경우

이를 통해 유효한 토큰과 실제 사용자가 확인된 요청만 처리할 수 있다.

### 1.3. `JWT_SECRET_KEY`가 없으면 어떻게 되는가? 왜 이렇게 구현했는가?

`JWT_SECRET_KEY`가 설정되어 있지 않으면 프로그램은 `RuntimeError`를 발생시키고 실행을 중단한다.

JWT의 서명을 생성하고 검증하려면 비밀 키가 필요하다. 키가 없는 상태에서 프로그램이 실행되도록 허용하면 인증 보안에 문제가 생길 수 있다. 따라서 `.env` 파일에 비밀 키를 설정하도록 하여 안전하지 않은 상태에서 프로그램이 실행되는 것을 방지한다.

## 2. `backend/assignments.py`

### 2.1. 모든 SQL에서 `WHERE ... AND user_id = ?`를 사용하는 이유는 무엇인가? 이 조건을 제거하면 어떻게 되는가?

`user_id` 조건은 각 사용자가 자신의 과제에만 접근할 수 있도록 사용자별 데이터를 분리하는 역할을 한다. 과제를 조회하거나 수정하거나 삭제할 때 해당 과제가 요청한 사용자에게 속하는지 확인한다.

이 조건을 제거하면 한 사용자가 다른 사용자의 과제를 조회하거나 수정 또는 삭제할 수 있는 보안 문제가 발생할 수 있다. 따라서 이 조건은 사용자 데이터의 무단 접근을 방지하는 데 중요하다.

### 2.2. `update_assignment`는 `changes` 딕셔너리를 사용하여 요청에 포함된 필드만 어떻게 수정하는가?

`update_assignment` 함수는 먼저 빈 `changes` 딕셔너리를 생성한다. 그다음 요청에 포함된 필드 중 값이 `None`이 아닌 필드만 딕셔너리에 추가한다.

예를 들어 `title`만 요청하면 제목만 수정한다. `completed` 필드가 요청되면 완료 상태뿐 아니라 `completed_at`도 함께 변경한다.

마지막으로 `changes`에 들어 있는 필드만 사용하여 SQL의 `SET` 부분을 생성한다. 수정할 필드가 없으면 `Nothing to update.`라는 HTTP 422 오류를 반환한다. 이렇게 하면 요청에 포함되지 않은 다른 필드의 값은 그대로 유지된다.

### 2.3. `completed_at`은 언제 설정하고 언제 `None`으로 변경하는가?

과제를 완료 상태(`completed = true`)로 변경하면 현재 UTC 시간을 `completed_at`에 저장한다. 반대로 미완료 상태(`completed = false`)로 변경하면 `completed_at`을 `None`으로 설정하며, 데이터베이스에는 `NULL`로 저장된다.

이미 완료된 과제를 다시 완료 상태로 변경하는 경우에는 기존 `completed_at` 값을 유지한다. 따라서 과제를 다시 완료 처리하더라도 최초 완료 시간이 불필요하게 변경되지 않는다.

### 2.4. SQL에서 `?` 파라미터를 사용하지 않고 값을 직접 삽입하면 어떤 위험이 있는가?

사용자 입력값을 SQL 문자열에 직접 연결하면 SQL Injection 공격에 노출될 수 있다. 공격자가 일반적인 데이터 대신 SQL 명령을 입력하면 데이터 조회, 수정 또는 삭제와 같은 의도하지 않은 작업이 실행될 가능성이 있다.

현재 코드는 `?` 플레이스홀더와 별도의 파라미터를 사용한다. 이를 통해 데이터베이스가 입력값을 SQL 명령의 일부가 아닌 데이터로 처리하도록 하여 SQL Injection 위험을 줄인다.

# Code Notes: Authentication and Assignments(몽골어)

## 1. `backend/auth.py`

### 1.1. `create_access_token` token дотор юу хадгалдаг вэ? `exp` юунд хэрэгтэй вэ?

`create_access_token` нь хэрэглэгчийн ID-г `sub` талбарт хадгалж, token дуусах хугацааг `exp` талбарт оруулдаг. `sub` нь тухайн token аль хэрэглэгчид хамаарахыг тодорхойлоход ашиглагдана.

`exp` нь token-ийн хүчинтэй хугацааг заадаг. Манай кодод энэ хугацааг `ACCESS_TOKEN_EXPIRE_MINUTES` тохиргоогоор тодорхойлдог бөгөөд анхдагч утга нь 30 минут. Хугацаа дууссан token-оор дахин нэвтрэх боломжгүй тул энэ нь аюулгүй байдлыг сайжруулдаг.

### 1.2. `get_current_user` token-ыг хэрхэн шалгадаг вэ? Ямар үед 401 буцаадаг вэ?

`get_current_user` нь хүсэлтийн Authorization хэсгээс Bearer token авч, `jwt.decode()` ашиглан token-ыг шалгадаг. Энэ үед нууц түлхүүр, тохируулсан алгоритм болон token-ийн хүчинтэй хугацааг шалгана. Дараа нь `sub` утгыг хэрэглэгчийн ID болгон хувиргаж, өгөгдлийн сангаас хэрэглэгчийг хайдаг.

Дараах тохиолдолд HTTP 401 алдаа буцаана:

- Token буруу эсвэл хугацаа нь дууссан.
- Token дотор `sub` байхгүй, эсвэл хэрэглэгчийн ID-г бүхэл тоо болгон хувиргах боломжгүй.
- Token-д заасан хэрэглэгч өгөгдлийн санд байхгүй болсон.

Ингэснээр хүчинтэй token болон бодит хэрэглэгчтэй хүсэлтийг л үргэлжлүүлэн боловсруулах боломжтой.

### 1.3. `JWT_SECRET_KEY` алга бол яах вэ? Яагаад тэгж хийсэн бэ?

`JWT_SECRET_KEY` тохируулаагүй бол програм `RuntimeError` алдаа гаргана. Ингэснээр нууц түлхүүргүй үед програмыг үргэлжлүүлэн ажиллуулахгүй.

JWT token-ийн гарын үсгийг үүсгэх болон шалгахад энэ түлхүүр шаардлагатай. Түлхүүр байхгүй үед програмыг ажиллуулах нь token-ийн аюулгүй байдлыг алдагдуулах эрсдэлтэй. Тиймээс `.env` файлд түлхүүрийг тохируулахыг шаарддаг.

## 2. `backend/assignments.py`

### 2.1. Бүх SQL-д `WHERE ... AND user_id = ?` байдаг. Үүнийг устгавал юу болох вэ?

`user_id` нөхцөл нь хэрэглэгч бүр зөвхөн өөрийн даалгаварт хандах боломжийг хангадаг. Жишээлбэл, даалгаврыг шинэчлэх эсвэл устгах үед тухайн даалгавар хүсэлт илгээсэн хэрэглэгчид хамаарах эсэхийг шалгана.

Хэрэв энэ нөхцөлийг устгавал нэг хэрэглэгч бусдын даалгаврыг харах, өөрчлөх эсвэл устгах эрсдэлтэй. Энэ нь хэрэглэгчдийн мэдээллийг тусгаарлах хамгаалалтыг алдагдуулна.

### 2.2. `update_assignment` зөвхөн илгээсэн талбарыг яаж шинэчилдэг вэ? (`changes` dict)

`update_assignment` нь эхлээд хоосон `changes` dictionary үүсгэдэг. Дараа нь хүсэлтээр ирсэн утга нь `None` биш талбаруудыг л энэ dictionary-д нэмдэг.

Жишээлбэл, зөвхөн `title` илгээвэл зөвхөн гарчиг шинэчлэгдэнэ. Харин `completed` талбар илгээсэн бол дууссан эсэхийн утгаас гадна `completed_at` талбарыг мөн шинэчилнэ.

Эцэст нь `changes` доторх талбаруудаас SQL-ийн `SET` хэсгийг үүсгэж, зөвхөн сонгосон талбаруудыг шинэчилдэг. Хэрэв шинэчлэх талбар байхгүй бол `Nothing to update.` гэсэн HTTP 422 алдаа буцаана.

### 2.3. `completed_at`-ийг хэзээ тавьж, хэзээ `None` болгодог вэ?

Даалгаврыг дууссан (`completed = true`) гэж тэмдэглэхэд `completed_at`-д одоогийн UTC цагийг хадгалдаг. Харин даалгаврыг дуусаагүй (`completed = false`) болгоход `completed_at`-ийг `None` болгож, өгөгдлийн санд `NULL` утга хадгална.

Хэрэв даалгавар өмнө нь дууссан бөгөөд дахин дууссан гэж тэмдэглэвэл анхны дууссан цагийг хэвээр хадгалдаг. Ингэснээр даалгаврыг дахин тэмдэглэх бүрд дууссан цаг шаардлагагүйгээр өөрчлөгдөхгүй.

### 2.4. `?` parameter ашиглахгүйгээр SQL-д утгыг шууд оруулбал ямар аюултай вэ?

SQL query-д хэрэглэгчийн оруулсан утгыг шууд залгаж оруулбал SQL Injection халдлагад өртөх эрсдэлтэй. Халдагч энгийн текстийн оронд SQL командын хэсэг оруулж, өгөгдөл унших, өөрчлөх эсвэл устгах боломжтой болж болзошгүй.

Манай код `?` placeholder болон тусдаа parameter ашигладаг. Ингэснээр өгөгдлийн сан утгыг SQL командын хэсэг биш, өгөгдөл гэж боловсруулна. Энэ нь SQL Injection эрсдэлийг бууруулдаг.
